PROBLEM
-------
Multi-machine setup was configured but requests only reached web1 and web2.
Web3 and web4 (on colleague's machine at 192.168.1.108) were never hit.

ROOT CAUSES FOUND
-----------------
1. Firewall on colleague's machine blocking ports 8003, 8004, 50053, 50054.
   The proxy health check sends HTTP to {container}/ping before routing —
   if that fails, the container is skipped entirely.

2. gRPC channels were built by stripping the port and hardcoding :50051.
   Remote containers expose gRPC on 50053 and 50054, not 50051, so all
   gRPC calls to web3/web4 would have failed even if health checks passed.

CHANGES MADE
------------
proxy/load_balancer.py
  - Added GRPC_URLS dict to store the gRPC address per container.
  - load_config() and reload_config() now read "grpc_url" from config,
    falling back to derived hostname:50051 for local containers.
  - reload_config() also cleans up GRPC_URLS on container removal.

proxy/main.py
  - startup_grpc_channels() now uses lb.GRPC_URLS[container] instead of
    hardcoded port 50051.
  - admin_reload() does the same for newly added containers.

config/config.json and config/config.remote.json
  - Added "grpc_url": "192.168.1.108:50053" to web3 entry.
  - Added "grpc_url": "192.168.1.108:50054" to web4 entry.

COLLEAGUE SETUP (no config changes needed on their side)
---------------------------------------------------------
They only run web3 and web4, not the proxy. They needed to:
  sudo ufw allow 8003
  sudo ufw allow 8004
  sudo ufw allow 50053
  sudo ufw allow 50054
  sudo ufw allow 2375
  docker compose up web3 web4

--- TEST 4: Traffic shaping — 10% packet loss ---

Commands:

  for i in {1..20}; do curl -s http://localhost:8080/test; echo; done
  curl -s http://localhost:8080/metrics
  sudo tc qdisc del dev wlp1s0 root

Expected:
  - Some requests to web3/web4 slower due to TCP retransmits
  - Possible 502s if gRPC times out

          request errors (errors_per_container all 0) because TCP
          recovered. Distribution remained even since algorithm is

NOTES

- Workload-based routing (X-Workload-Type header) routes memory workloads
  to web2/web4 and cpu workloads to web1/web3. Observed to not always filter
  correctly under round_robin — switching to active_probe is recommended for
  production use as it respects probe health when selecting candidates.

- Colleague does not need to pull or change any config. All proxy-side changes
  live in proxy/ and config/, which only the proxy machine uses.
